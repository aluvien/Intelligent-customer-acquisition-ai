# Markdown 与源码核对

仓库 Markdown 是历史资料，不直接作为已验证能力。以下结论记录改造前 `38f37ce` 的源码核对结果；当前实现以最新 `main`、`README.md` 和 `docs/rebuild/STATUS.md` 为准。

## 关键冲突

| 文档结论 | 源码事实 | 处理 |
|---|---|---|
| OAuth 后可以通过 live-im-proxy 监听 | Go 的 OAuth、账号保存和渠道监听仍为内存实现，WS 协议未被真实验证 | 标记 `unverified`，T7 单独核验 |
| 已支持多平台/私信/评论回复 | Go pipeline 只放行 `comment`，不同平台实现和权限没有真实证据 | 不标记为已接入 |
| 测试完成/生产可用 | 现有测试主要是参数和模拟路径，业务记录没有数据库持久化 | 重新建立可重复验收 |
| 两仓库三服务是当前部署结构 | 当前代码是单仓库，Node、Go、前端、Compose 配置职责重叠 | T1 统一 Compose，Go 设为可选适配器 |
| MySQL/PostgreSQL 均可用 | Node 没有数据库访问层，Compose 仅声明 PostgreSQL | 统一 PostgreSQL |

## 重点文件结论

- `README.md`、`RAILWAY_DEPLOY.md`、`启动说明.md`：保留为部署参考，T9 更新为当前单仓库结构。
- `实现进度报告.md`、`测试结果总结.md`、`模拟测试报告.md`：不能作为真实收发证据。
- `技术方案重新梳理.md`、`抖音接口使用说明.md`、`access_token与live-im-proxy对接分析.md`：涉及平台协议的部分需要官方文档和真实账号重新核验。
- `Coze配置指南.md`：旧式调用说明与当前服务实现不一致，T5 只按实际供应商协议实现。
- 历史文档中出现疑似应用密钥的位置已纳入 T1 脱敏清单；删除当前树中的值不等于凭据已失效，必须由账号所有者轮换。
